# rag-core target design

rag-core stops being a question-answering agent and becomes a pipeline that prepares documents for one model call.
The code decides which documents the model sees and which facts are attached to each; the model only describes
them. The same question gives the same documents and the same flags every time.
The model does not answer the consultant's question. It ranks the documents in scope, says what stands out in each,
and gives a short spoken summary. The prompt that defines this is `PROMPT` in `src/rag_core/relevance.py`; it leads,
and everything below exists to feed it.

## Data contract

`data/catalog.json` (on `main`, generated by `scripts/build_data.py`) is the only metadata source. Its values are
shown to the consultant and to the model exactly as stored: nothing is extracted, inferred or overridden.
`data/users.json` says which consultant is assigned to which clients. Document text comes from the PDF at each
entry's `path`, relative to `data/`.

This replaces rag-core's earlier metadata model (six fields from a JSON file next to each PDF, or filled by a model,
with per-field provenance). Catalog field names win: `domain`, not `department`; `last_updated`, not `updated_at`.

## Pipeline

1. **Identity.** The consultant comes from the login session, never from the question text. The selected client
   comes from the UI.
2. **Scope** (`catalog.scope`). General documents (everything outside `clients/`) plus the selected client's own
   documents. Raises `AccessDenied` when the consultant is not assigned to that client. Other clients' documents are
   left out even when the consultant is assigned to them too. A file under `clients/` whose client cannot be read
   from `client_id` or from its `clients/<client_id>_<slug>/` folder is left out.
3. **Flags** (`catalog.compute_flags`). Computed from the scope only: `supersedes` and `overrides` as stored, their
   reverses `superseded_by` and `overridden_by`, `owner_left`, `owner_moved` and `no_owner` from `owner_status`,
   `draft` and `informal` from `status`, and `stale` when `last_updated` is more than 2 years before the
   current date, so the model never does date arithmetic. A link whose target is outside the scope is dropped.
4. **Candidates.** The documents shown to the model, a subset of the scope. When the context names a domain,
   only documents of that domain are shown, plus the client's profile and handover notes (domain `Client`). Flags stay computed over the whole
   scope, so a shown document can point to one that was not selected; the prompt tells the model to say so.
5. **Split by country and entity.** Documents for another country (not `ALL`) than the context names, or client
   documents for another entity than the context names, go to the second list.
6. **Tags** (`catalog.document_tag`). Attributes come from the allowlist `TAG_FIELDS`; `path`, `topics`,
   `owner_status` and any evaluation label never reach the model. Attribute values and document text are
   HTML-escaped, so document text cannot close its tag.
7. **Prompt** (`relevance.build_prompt`). Placeholders are filled in one pass, so a `{DOCUMENTS}` typed in a
   question stays literal.
8. **Model call and validation.** One call, JSON out. Still to build: see below.

## Why scope comes first

Two leaks shaped the order above. Relationship flags computed over the whole catalog reveal other clients: for a
consultant working for Brouwerij Delta, the Belgian legal overtime rule would carry
`overridden_by:CL-20318-BE-001`, the ID of a Havenlink document that consultant may not see. And copying catalog entries into tag
attributes passes `security_test: prompt_injection`, which labels the injection test document and gives the model the
answer to the test. Both are prevented by construction: only `scope` reads the whole catalog, and tags use an
allowlist rather than a list of hidden fields.

## Still open

- **Candidate selection.** `build_prompt` shows the whole scope unless given `candidates`. The BM25 index in
  `search.py` can supply them, filtered by the context's country and domain.
- **Context extraction.** Something must fill `{CONTEXT}` (country, entity, domain) from the question and chat
  history. Mapping a site to an entity ("Antwerp" to Brouwerij Delta NV) needs the sites, which today exist only in
  the client profile PDF's text.
- **Client registry.** `{CLIENT}` wants a name ("CL-10045 Brouwerij Delta"), but `users.json` holds only client IDs.
  Add a client list with names, entities and sites to the data system.
- **Evaluation label.** Move `security_test` out of `catalog.json` into a separate file of expected outcomes (for
  example `data/eval_cases.json`), so the running system never loads it. The allowlist already keeps it from the
  model.
- **Model call.** Send the prompt, parse the JSON, reject IDs that were not shown, and map `[n]` citations to
  document IDs for the UI.
- **Retire.** The tool-using agent loop and its system prompt (`agent.py`), the sidecar metadata model and the
  model-based metadata extractor (`ingest.py`, `models.py`, `providers.py`), and the `/ask` response shape
  (`app.py`). PDF text extraction, content hashing, the BM25 index, `OpenAICompatibleProvider` and the FastAPI server
  stay.
